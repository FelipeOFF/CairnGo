Uma checagem nova no `cairn-doctor.py`, `req-ledger`, na forma exata das que já
estão lá: uma função `check_req_ledger(...)` devolvendo
`{"id": "req-ledger", "status": "ok"|"fail", "detail": …, "items": [...]}`, somada à

**Os elos, e são quatro de propósito:**
  - **requisito ativo → linha na tabela.** Todo requisito da seção de requisitos do
    milestone corrente tem linha na tabela de Cobertura. Requisito em `## Deferred`

    excluídos por essa regra — ausência explicada não é falha, mas silêncio sobre
    ela é a falha na direção oposta.
  - **tabela → rodapé.** O número que o rodapé `N requisitos, N mapeados.` afirma
    bate com a contagem de linhas da tabela.
  - **linha `**Requirements**:` legível.** Uma fase cuja linha de requisitos não
    produz a lista de ids que a seção de requisitos lhe atribui é falha nomeada, com

    uma vez, e sem ele o `req-ledger` herdaria o mesmo ponto cego que faz o
    `req-issue` dizer 29.

Cada elo rompido vira um item com o subject nomeado: o id do requisito sem linha, os
dois números que discordam, a fase cuja linha é ilegível, o plano cujo checkbox

dizer **qual** requisito e **quais** números.

**A leitura vem do `cairn-bookkeep.py reconcile --json`, por subprocess.** Não
reimplemente o parser do ledger aqui. O ponto do requisito é a cadeia ter **uma**
leitura; duas implementações que podem discordar sobre 35/33/29 é exatamente o
defeito com mais um número.

**E aqui está a armadilha que quase inutilizou esta checagem, medida linha a linha.**
O formato defensivo que este arquivo já usa em `check_phase_corroboration()`
(`cairn-doctor.py:1121-1128`) é `if proc.returncode not in (0, 5): return {"status":
"warn"}`. Copiá-lo sem trocar a allowlist quebraria a checagem de três maneiras
encadeadas:

  1. `cairn-bookkeep.py reconcile` sai **3** quando há discordância — é o contrato do
     29-01, e espelha o `cairn-reconcile.py:154` (`EXIT_NOT_CONFLICTED = 3`) e o
     `--check` do `cairn-map.py`. Com allowlist `(0, 5)`, **o único caso que a
     checagem existe para reprovar cairia no ramo de "ferramenta indisponível"**;
  2. esse ramo devolve `warn`, e `cairn-doctor.py:273-274` documenta que aviso
     **nunca** muda o exit code;
  3. logo o doctor sairia **0** — e a prova de aceitação deste plano, que exige exit
     **7**, seria inalcançável. Pior: o teste que afirma "o status nunca é `ok`"
     ficaria **verde**, porque `warn` não é `ok`. Uma checagem contra verde falso,
     produzindo verde falso, aprovada por um teste que não percebe.

**Então a allowlist é declarada em número e o mapeamento é explícito:**

  - returncode **0** → o JSON é lido; `ok` se nenhum elo rompido, `fail` se houver
    (o `reconcile` pode sair 0 num repo já consistente);
  - returncode **3** → `fail`. É o verdito de discordância, e é o caso normal desta
    checagem hoje;
  - **qualquer outro código, script ausente, ou JSON ilegível** → `fail`, com
    `detail` nomeando a indisponibilidade e o motivo. **Nunca `warn`, nunca `ok`.**

Escreva no código, em comentário ao lado da allowlist, por que ela é `(0, 3)` e não
`(0, 5)`, com a referência ao contrato do `cairn-bookkeep.py`. Um número mágico
copiado de uma checagem vizinha é como esta armadilha nasce.

**Por que indisponibilidade é `fail` e não `warn`.** Uma checagem que aprova por não
ter conseguido checar é a doença que o milestone v1.5 inteiro existe para eliminar, e
`warn` deixa o doctor verde — o que é aprovar. `not-applicable` (VOID-01, fase 23) é
para "não há o que checar", que é outra coisa: sem tabela `## Cobertura` no ROADMAP a
checagem de fato não se aplica. "Não consegui ler o ledger" não é "não há ledger".

**Sem `## Cobertura` no ROADMAP** (roadmap de outro projeto, ou vazio): a checagem
não se aplica — não invente falha onde não há tabela. Se a fase 23 já tiver entregue
`not-applicable` como estado de primeira classe quando este plano rodar, use-o; se
não, use o idioma de skip que o doctor já tem, com um comentário apontando o
`VOID-01`. Não antecipe o estado novo: a fase 23 é dona dele.
