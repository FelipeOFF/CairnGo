tool-restricted subagent that reads Plan 17-01's evidence bundle plus its own
further code/git/memory reads and writes a cited proposal, and the
`/cairn:reconcile <N>` command that orchestrates gate -> cache-check ->

**Locked decisions this plan implements:**
- D-01: "subagente restrito → lê o pacote, escreve a proposta" — the middle
  layer of the pipeline. Its write incapacity is a harness-level guarantee
  (tool grants), which is real but — per D-01's own recorded reasoning —
  insufficient ALONE for the roadmap's grep+bats criterion; Plan 17-01
  already supplied the grep-provable half. This plan's job is the semantic
  half D-01 says a script cannot do: "perde a leitura semântica, que é
  literalmente o que o ESC-01 pede."
- D-02: the proposal is written to `.cairn/conflicts.json` (gitignored,
  reserved since v1.0) — this plan is the first thing that ever writes it.
- D-04: the cache lives in `/cairn:reconcile`'s own logic — before spawning
  the subagent, compare a fresh `collect --json`'s `evidence_hash` against
  any existing `.cairn/conflicts.json` for the same phase; a match means the
  cached proposal is still valid and the subagent is never re-invoked.
- ESC-04's "roda apenas sobre conflito detectado" is enforced TWICE by
  construction: Plan 17-01's `collect` refuses mechanically (exit 3), and
  this command checks corroboration itself before calling `collect` at all
  — so a bats test against this command's own source can assert the gate
  check precedes every other step, without needing a live LLM.

**Proposal schema (fixed in 17-01, reused verbatim here — do not diverge):**
```
{
  "phase": <int>, "generated_at": <iso8601>, "evidence_hash": "sha256:<hex>",
  "claims": [{"statement": "...", "citations": [{"file":..., "line":..., "text":...}],
              "recommended_action": {"type": "bd_close"|"bd_reopen"|"manual_review", ...}}]
}
```
The `recommended_action` vocabulary is intentionally small and closed —
`bd_close`/`bd_reopen` (Plan 17-03's applier executes these two, and only
these two, as real writes) and `manual_review` (no automated action exists;
Plan 17-03 enumerates it and does nothing else). The subagent must never
invent a fourth action type — instruct it explicitly to pick one of exactly
these three, mapped from corroborate()'s own conflict source pairs
(disk-vs-bd -> bd_close or bd_reopen depending on which side is behind;
roadmap-vs-disk and state_md-vs-disk -> manual_review, since neither has a
safe, generic automated fix — this mirrors how cairn-doctor.py itself never
auto-edits ROADMAP.md/STATE.md, only ever `bd` subprocess writes).
