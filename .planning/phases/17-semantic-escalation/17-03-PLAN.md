<objective>
Add `cairn-doctor.py --apply-reconciliation <N>`: the human-invoked, separate
command that reads a verified reconciliation proposal, enumerates every
change it is about to make, and only then applies the small, closed
`bd_close`/`bd_reopen` action vocabulary — refusing outright if the
proposal's evidence has gone stale or its citations no longer check out.

Purpose: this is ESC-03 in full — "aplicar é comando separado, invocado por
humano, que enumera cada mudança antes de fazer qualquer uma." It follows the
exact fixer-flag shape `--close-completed` and `--link-refs` already
established in this same file: read-only by default, a named flag performs
writes, the report shows post-fix state, nothing is ever silent.

Output: the new flag on `cairn-doctor.py`, its docstring/exit-code entries,
`cairn/commands/doctor.md` updated to document it, and
`tests/cairn-doctor.bats` scenarios proving enumeration-before-mutation,
staleness refusal, and invalid-citation refusal.
</objective>

**Locked decisions this plan implements:**
- D-01: `cairn-doctor.py --apply-reconciliation` is the fourth and final
  layer of the pipeline — "humano, enumera antes de mudar." It is the ONLY
  place in the whole phase where a real `bd` write happens.
- ESC-03 verbatim: "Aplicar uma proposta é um comando separado, invocado por
  humano, que enumera o que vai mudar antes de mudar."
- This plan's own defense in depth (Claude's Discretion, consistent with
  D-03's spirit): re-run BOTH the evidence-hash freshness check (via
  `cairn-reconcile.sh collect <N> --json`, comparing its `evidence_hash`
  against the proposal's stored one) AND the citation re-check (via
  `cairn-reconcile.sh verify <N>`) at apply-time, not just at proposal-
  generation time in Plan 17-02. A proposal is only ever as trustworthy as
  its LAST verification — time may have passed between `/cairn:reconcile`
  producing it and a human running `--apply-reconciliation`, during which
  the underlying phase state (or the cited files) could have changed.
- **Issue-provenance check (plan-check warning fix, added in this
  revision):** citation verification proves a claim's *evidence* is real,
  but nothing previously confirmed the bd id a `bd_close`/`bd_reopen`
  action actually TARGETS is one of the ids that genuinely belongs to the
  phase being reconciled — a proposal could carry perfectly correct
  citations and still name an unrelated issue, with only a human reading
  the enumeration as a (soft) backstop. This plan closes that gap the same
  fail-closed way as a stale hash or a bad citation: before enumerating
  anything, cross-check every `recommended_action.issue` against the bd
  issues actually labeled `phase-N` — reusing `check_phase_complete_open`'s
  own `phase_nums()`-based label filter over `issues` (already loaded once
  in `main()` via `bd_all_issues(root)`, no new bd query needed). An id
  that isn't a phase-N issue refuses the WHOLE apply, not just that one
  claim.

**The closed action vocabulary this flag executes** (fixed in 17-01/17-02,
reused verbatim — do not add a fourth type here):
- `bd_close`: `bd -C <root> close <issue> --reason "<reason>"`
- `bd_reopen`: `bd -C <root> update <issue> --status open --assignee ""`
  (mirrors the existing release-shape already used elsewhere in this
  codebase for "clear a stale claim")
- `manual_review`: never executed — enumerated with its `note`, then skipped
  explicitly, printed as "skipped (manual review, no automated action)" so
  it is visibly accounted for, never silently dropped from the list.
Nothing outside these three `recommended_action.type` values is ever
executed; an unrecognized type refuses the WHOLE apply (fail closed, same
posture as a stale hash or a bad citation) rather than skipping just that
one claim — the proposal's trustworthiness is all-or-nothing, matching D-03's
own "not a proposal with an error, a proposal you cannot trust" framing
extended from citations to the action vocabulary itself.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| .cairn/conflicts.json -> --apply-reconciliation | The only place in the entire phase where an artifact originating from an LLM's investigation turns into a real `bd` write — every other layer is either fully deterministic or fully read-only. (The file itself is written by `/cairn:reconcile`'s own deterministic code, per Plan 17-02's revision — the trust boundary is the LLM-authored *content*, not the write syscall.) |
| operator's --apply-reconciliation invocation -> bd | A human explicitly running this flag is the ESC-03 "invoked by human" consent; the enumeration is what makes that consent informed, not blind |
| recommended_action.issue -> the actual phase being reconciled | Correct citations prove a claim's evidence is real; they say nothing about whether the bd id a claim targets even belongs to this phase — a second, independent boundary this plan's issue-provenance check (Task 1, step 4) closes |
