# Fase 30 Plano 01 — "isto entrou?", respondido do git local, sem rede

## O problema

O board não sabe nada sobre a branch de controle. Medido em 2026-08-05 e
reconfirmado hoje: `git merge-base --is-ancestor 6545a5c origin/main` é falso,
`git rev-list --count origin/main..HEAD` é **145**, e nenhuma superfície do
cairn diz uma palavra sobre isso.

## O que este plano entrega

Um script novo, `cairn-land.py`, que é o **único dono** da leitura do git para
esta pergunta, e a integração dele no board.

### Task 1 — `cairn-land.py`, o dono da pergunta

Três verbos, no padrão do `cairn-jira.py` (detectar → mostrar → confirmar uma
vez → gravar sozinho):

- `detect` — candidatas a branch de controle, com evidência e a fonte de cada
  uma. Precedência: `refs/remotes/origin/HEAD` → nomes convencionais em
  `git branch -r`/`git branch` (`develop`, `dev`, `main`, `master`, `trunk`) →
  a branch de que a atual mais descende. **Medido: `git symbolic-ref
  refs/remotes/origin/HEAD` sai 128 neste repositório**, então a fonte mais
  óbvia não existe aqui e a detecção degrada em vez de morrer.
- `apply --branches a,b` — grava `git.control_branches` **através do
  `cairn-config.py`**, que é o dono do `.cairn/config.json`. Este script nunca
  abre aquele arquivo.
- `report [--json]` — o veredito de aterrissagem por fase.

**O modelo de aterrissagem, e a razão de cada escolha:**

| pergunta | como |
|---|---|
| quais commits são de uma fase | (a) tocaram `.planning/phases/NN-*/`; (b) o escopo do conventional commit nomeia a fase (`feat(29-05)`, `chore(29)`) |
| o commit entrou na branch | ele **não** está em `git rev-list HEAD --not <branch>` |

A segunda linha é a inversão que torna a leitura barata **e** exata: o conjunto
"não entrou" é `origin/main..HEAD`, que vale **145** aqui e é justamente a
quantidade que um repo saudável mantém pequena. Uma chamada por branch de
controle, e o teste de ancestralidade vira pertinência de conjunto — o mesmo
veredito que `git merge-base --is-ancestor` dá, sem uma chamada por par.

Medido para justificar a atribuição por escopo: **313 dos 530** commits de HEAD
carregam escopo de fase, e o commit de fecho da fase 29 (`6545a5c`) **não toca**
`.planning/phases/29-*/` — ele mexe em ROADMAP/STATE/REQUIREMENTS. Só a fonte
(a) perderia esse commit; só a (b) perderia um repo que não usa esse escopo.

Vocabulário do veredito, valores exatos, nunca negações:
`landed` (todos os commits atribuídos entraram) · `partial` (alguns) ·
`unlanded` (nenhum) · `unknown` (nenhum commit atribuído, ou o git não pôde ser
lido) **com motivo nomeado**.

### Task 2 — o board consome, e a prova de rede continua de pé

- `cairn-status.py` chama `cairn-land.py report --json` por
  `sys.executable` — o **quinto** sítio de `subprocess.run`, e ele está na
  allowlist da camada 3 justamente por ser `sys.executable`.
- `phases[].landed` no `--json`, e `landed` em cada issue por **projeção do
  rótulo `phase-N`**. Medido, e é por isso que a projeção é a fonte certa: 41
  linhas de corpo de commit citam um id do bd, e todas as amostradas são
  referências em prosa (`bd issue CairnGo-gbu`, `(CairnGo-0rk)`), não
  atribuições. Atribuir trabalho por menção seria inventar um vínculo.
- Sufixo condicional ao dado na linha da fase e na linha da tarefa da lista
  agrupada, exatamente como o `29-05` fez com o `⧉`.
- `tests/cairn-tracker-card.bats`: o literal `ok: 4 subprocess.run sites` passa
  a 5, com o motivo escrito ao lado.
