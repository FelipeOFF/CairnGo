<objective>
Add automatic, size-triggered compaction to cairn-journal.py (D-03): fold
every phase's full event history into one `snapshot` record per phase,
write those snapshot records to a NEW sibling file, then swap it into place
with `os.rename` — never a rewrite of the live journal in place.

Purpose: the journal is scoped to a project's entire lifetime with no
natural discard point (unlike cairn-migrate.py's per-run resumable
journal, which gets thrown away after one migration). Left unbounded,
every `history`/`last-moved` read gets slower every month. Compaction has
to be designed in from the start (JOUR-05), not bolted on once growth
becomes a visible problem, and it has to prove — mechanically, not by
narration — that the compacted file answers "when did each side last
move" identically to the full, uncompacted replay.

Why rename and not an in-place rewrite: the journal exists specifically
to survive a crash. Rewriting in place puts a rewrite on the exact path a
crash does the most damage — a crash mid-rewrite doesn't leave a torn
LINE (which Plan 16-01's Task 3 already knows how to quarantine), it
leaves the WHOLE FILE in an indeterminate state. With the sibling-file-
then-rename approach, a crash mid-compaction leaves the original journal
completely untouched and only an orphaned temp file behind.

Output: `compact` subcommand, wired as an automatic pre-write check inside
`observe`/`lease`, plus the replay-equivalence bats test that is JOUR-05's
actual acceptance criterion.
</objective>

  <behavior>
    - `compact [--project-dir D] [--json]` on a journal that does not
      exist yet: no-op, exit 0, creates nothing (never fabricates an
      empty journal file).
    - `compact` on a real journal with events across multiple phases:
      folds each phase's full history (via `_last_known()`, already
      built) into exactly one `snapshot` record per phase carrying
      `state` (the four evidence axes, each `{"value":..., "ts":...}` or
      null), `verdict` (`{"value":..., "ts":...}` or null), `lease`
      (`{"value":..., "holder":..., "ts":...}` or null), and
      `compacted_through_ts` (the `ts` of the latest real event folded
      in). Writes these snapshot records — and ONLY these, nothing else
      — to a brand-new file via `tempfile.mkstemp(dir=journal_path.parent,
      prefix="journal.jsonl.tmp-")`, closes it, then `os.rename(tmp_path,
      journal_path)`.
    - The size threshold that triggers automatic compaction is a named
      module constant (`JOURNAL_COMPACT_THRESHOLD_BYTES`, pick something
      in the low hundreds of KB — small enough this task can test it
      without padding a multi-megabyte fixture, large enough that routine
      day-to-day phase work does not compact every few appends;
      document the reasoning in the docstring, not just the number).
      `observe` and `lease` both check the journal's current byte size
      BEFORE opening for append, in the SAME process invocation, and call
      `compact()` first if over threshold — never as a background
      process (each `/cairn:*` invocation is already a single short-lived
      process per this codebase's existing model; a background compactor
      would just be a second process racing the first for no benefit).
    - A second `compact` call (or a concurrent `observe`/`lease` that
      would trigger auto-compaction) while one compaction is already
      mid-flight: the second caller's compaction attempt is SKIPPED
      (non-blocking `fcntl.flock(LOCK_EX | LOCK_NB)` on a dedicated lock
      file, e.g. `journal.jsonl.compact.lock`, sitting next to the
      journal — held only for the read-fold-write-rename critical
      section) — the second caller's own append still proceeds normally
      immediately afterward, uncompacted-but-correct; it is never blocked
      waiting for the other compaction to finish.
  </behavior>
