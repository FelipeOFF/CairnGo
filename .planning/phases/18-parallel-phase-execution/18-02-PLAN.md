<objective>
Acrescentar o subcomando `reconcile` a `cairn-parallel.py`: um relatório
read-only que, para cada branch `phase/<N>-<slug>`, diz o que aquela fase
produziu e, para cada par de branches, nomeia **a edição convergente** — a
linha que as duas mudaram para o mesmo valor, que o git resolve sozinho e não
reporta.

Purpose: esta é a única parte da fase que ninguém mais faz. Conflito de merge
o git já reporta e reporta bem (medido: `git merge-tree --write-tree` sai 1 e
nomeia o arquivo). O que passou despercebido quando as fases 14 e 15 foram
mescladas neste repo foi o outro lado: as duas mudaram a mesma contagem de
`13` para `14` por razões diferentes, o git viu duas mudanças idênticas e
tomou uma, e a árvore ficou com **15 checagens, um docstring dizendo 14 e dois
itens numerados 13**, com zero conflitos reportados. O merge estava limpo e
estava errado. `reconcile` existe para que essa classe interrompa alguém.

Output: o subcomando `reconcile` no mesmo arquivo, o comentário de exit codes
do wrapper atualizado em lockstep, e os testes que reproduzem o incidente
14/15 como fixture.
</objective>

`cairn-reconcile.py` entra como MOLDE, não como lugar para escrever: é o
coletor da fase 17, e dele se copia a disciplina — script que só relata, cuja
ausência de escrita é provável por grep e por um teste que roda contra fixture
e afirma que nada mutou. O subcomando novo vai em `cairn-parallel.py`.

**Decisão travada que este plano implementa (18-CONTEXT.md):**
- **D-02**: detectar e reportar a edição convergente, além do conflito de
  merge comum. Uma linha que as duas branches tocaram é sinalizada **mesmo
  quando o git a resolveu sozinho por serem idênticas**.
- **D-03**, metade de relato: escrita de branch de fase em `STATE.md` /
  `ROADMAP.md` / `REQUIREMENTS.md` aparece como achado nomeado. **Não** faz o
  comando falhar — "falhar a reconciliação quando uma branch de fase tocou
  arquivo de planejamento" está em `<deferred>` da CONTEXT.md, e relatar não é
  falhar.

**Comportamento do git medido nesta sessão (git 2.42.1), não suposto:**
- `git merge-tree --write-tree A B`: sai **0** limpo, **1** com conflito;
  stdout começa pelo oid da árvore, lista as entradas em conflito com número
  de estágio e depois um bloco informativo com linhas
  `CONFLICT (content): Merge conflict in <path>`.
- Duas branches mudando a mesma linha `checks = 13` para `checks = 14`, sem
  outra sobreposição: `merge-tree` sai **0**, e o `git merge` real diz
  `1 file changed` sem sequer citar o arquivo convergido. Este é o fixture do
  incidente, e ele é exatamente reproduzível.
- Duas branches acrescentando linhas DIFERENTES no mesmo ponto de inserção:
  o git conflita e reporta. Ou seja, "dois itens numerados 13" o git pega; a
  contagem convergida ele não pega. A divisão de trabalho entre git e cairn
  cai exatamente aí.
- `git diff -U0 <base>..<branch>` dá o hunk na forma `@@ -a,b +c,d @@`, que é
  a matéria-prima da detecção: faixa de linhas da BASE substituída por um
  bloco de linhas novas.

    - `reconcile [--phases 7,9] [--project-dir DIR] [--json]`.
    - Descoberta: `git for-each-ref --format='%(refname:short)' refs/heads/phase/*`,
      número da fase extraído do nome pela MESMA regra que `prepare` usou para
      nomear. Nenhuma outra fonte — não se pergunta a agente nenhum onde ele
      trabalhou (D-01). `--phases` restringe.
    - Por branch, `produced`: `git rev-list --count <merge-base>..<branch>` e
      `git diff --numstat <merge-base>..<branch>`, com `merge-base` calculado
      contra `HEAD`. Devolve `{phase, branch, commits, files, insertions,
      deletions}` — é isto que responde "o que cada fase produziu" (PAR-04).
    - `planning_writes`: por branch, quais de `.planning/STATE.md`,
      `.planning/ROADMAP.md`, `.planning/REQUIREMENTS.md` aparecem no diff.
      Achado nomeado, **sem efeito no exit code** (D-03 / `<deferred>`).
    - Por par não ordenado de branches: base = `git merge-base X Y`. Para cada
      arquivo alterado nos DOIS lados, os hunks de `git diff -U0 base..X` e de
      `git diff -U0 base..Y` viram tuplas `(início na base, tamanho na base,
      linhas novas)`. **Edição convergente** = mesma faixa da base nos dois
      lados E bloco de linhas novas byte a byte idêntico. Reporta
      `{file, base_line, new_lines, branches: [X, Y]}` com o texto truncado a
      200 caracteres por linha.
    - O limite da afirmação vai escrito no docstring: convergência é declarada
      só na igualdade estrita de faixa e de conteúdo. Sobreposição parcial com
      conteúdo diferente é conflito, e conflito é do git. O que este script
      afirma é exatamente o que ele mede.
    - `conflicts`: `git merge-tree --write-tree X Y` por par. Código 0 -> lista
      vazia; código 1 -> uma entrada por linha `CONFLICT (...): ... in <path>`;
      qualquer outro código, ou stderr indicando opção desconhecida ->
      `conflicts: null` mais `conflicts_note` dizendo que a versão do git não
      pré-calcula conflito e que o git os reportará na hora do merge. Nunca
      lista vazia por falha (Pitfall 3: falhar aberto reproduz o bug que este
      milestone existe para matar). O relatório carrega `git_version`.
    - Nenhuma leitura de working tree de worktree viva: só `git diff`,
      `git merge-tree`, `git rev-list`, `git for-each-ref` sobre refs
      commitadas (Pitfall 15 — ler arquivo que outro agente está editando
      produz relatório confiantemente errado).
    - Exit: `EXIT_OK` quando não há conflito nem edição convergente;
      `EXIT_FINDINGS=6` quando há qualquer um dos dois, **e também** quando
      `conflicts` é null — nesse caso o script não pode dizer que está limpo,
      e não vai dizer. `6` segue a leitura da casa ("gate failed") e é o
      mecanismo que impede um passe silencioso; ele não resolve nada.
    - Modo humano: uma seção por categoria, cada achado com `arquivo:linha`, e
      a linha final dizendo o total. Modo `--json`: `{git_version, branches:
      [...], pairs: [{branches, convergent_edits, conflicts, conflicts_note}],
      planning_writes, findings_total}`.
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| branches `phase/*` -> relatório | qualquer branch com esse nome entra no relatório; o nome é a única credencial |
| conteúdo de diff -> stdout | linhas de arquivo do repo são ecoadas no relatório |
| versão do git -> afirmação de limpeza | o que o script pode afirmar depende de um binário externo |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-18-05 | Spoofing | descoberta de branches por nome | medium | mitigate | `reconcile` só relata; ele nunca faz merge, então uma branch `phase/*` forjada vira uma linha de relatório, jamais um commit na árvore principal. O relatório carrega commits e merge-base de cada branch, para o operador ver a procedência |
| T-18-06 | Repudiation | merge limpo com convergência silenciosa | high | mitigate | achado nomeado com arquivo e linha + exit 6; um relatório não-vazio não pode ser confundido com sucesso por um chamador com `set -e` |
| T-18-07 | Information Disclosure | eco do conteúdo das linhas convergidas | low | mitigate | só as linhas convergentes, truncadas em 200 caracteres, e só de refs que o operador já tem localmente |

| T-18-09 | Tampering | leitura de arquivo em edição por outro agente | medium | mitigate | só refs commitadas; nenhum caminho de working tree de worktree viva é lido (Pitfall 15) |
