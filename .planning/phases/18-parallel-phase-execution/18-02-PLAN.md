read-only que, para cada branch `phase/<N>-<slug>`, diz o que aquela fase
produziu e, para cada par de branches, nomeia **a edição convergente** — a

itens numerados 13**, com zero conflitos reportados. O merge estava limpo e
estava errado. `reconcile` existe para que essa classe interrompa alguém.

Output: o subcomando `reconcile` no mesmo arquivo, o comentário de exit codes
do wrapper atualizado em lockstep, e os testes que reproduzem o incidente

**Comportamento do git medido (git 2.42.1), não suposto:**
- `git merge-tree --write-tree A B`: sai **0** limpo, **1** com conflito;
  stdout começa pelo oid da árvore, lista as entradas em conflito com número
  de estágio e depois um bloco informativo com linhas `Auto-merging <path>` e
  `CONFLICT (content): Merge conflict in <path>`. **`Auto-merging` não é
  aviso de nada** — é o git dizendo que juntou o arquivo sem problema.
- **A forma real do incidente, medida sobre os dois pais reais do merge
  (`b9c608f`/`b0466aa` de `672e754`, ver D-02):** o git reportou **um**
  conflito, e num arquivo que não era o do dano
  (`cairn/docs/commands/doctor.md`); `tests/cairn-doctor.bats` e
  `cairn/scripts/cairn-doctor.py`, que carregam a contagem convergente **e**
  o bloco distinto que cada fase acrescentou, mergearam **limpos**.
- **Reproduzido nesta sessão em fixture sintético com a forma real** (contagem
  `13`->`14` idêntica nos dois lados na linha 1, mais um bloco distinto por
  lado, cada um num ponto diferente e distante do arquivo): `merge-tree` sai
  **0**, o `git merge` real sai **0** e imprime `Auto-merging checks.txt` +
  `1 file changed`, e o arquivo resultante tem `checks = 14` com **dois itens
  numerados "check 13"**. O incidente inteiro, inclusive a numeração
  duplicada, num merge limpo. Hunks `-U0`: `@@ -1 +1 @@` nos DOIS lados, faixa
  e conteúdo idênticos — é exatamente o que a igualdade estrita pega.
- **Correção de redação, medida:** nessa forma real o `git merge` **cita** o
  arquivo (em `Auto-merging` e no diffstat), porque as duas branches mexeram
  nele em pontos diferentes. O que ele não faz é reportar **conflito** nele. A
  asserção do teste é portanto "o merge sai 0 e não reporta conflito neste
  arquivo", e não "o merge não cita o arquivo" — esta última só é verdadeira
  na classe silenciosa pura, e lá ela fica.
- **Classe silenciosa pura, medida:** quando a única mudança comum no arquivo é
  a linha convergente e cada branch mexe só em arquivos seus, o `git merge`
  não cita o arquivo **de forma alguma** — o diffstat lista apenas o arquivo
  do outro lado. É o caso mais mudo dos dois.
- Duas branches acrescentando linhas DIFERENTES no MESMO ponto de inserção: o
  git conflita e reporta. A divisão de trabalho cai aí: bloco distinto no
  mesmo lugar o git pega; contagem convergida ele não pega, em lugar nenhum.
- `git diff -U0 <base>..<branch>` dá o hunk na forma `@@ -a,b +c,d @@`, que é
  a matéria-prima da detecção: faixa de linhas da BASE substituída por um
  bloco de linhas novas. **Limite medido:** quando o bloco acrescentado é
  ADJACENTE à linha convergente, o `-U0` funde os dois num hunk só, as faixas
  ficam iguais mas o conteúdo novo difere, e a convergência não é declarada.
  Nesse arranjo o git conflita de verdade, então o operador para de qualquer
  jeito — mas o limite é do detector e vai escrito no docstring, não
  encoberto.
