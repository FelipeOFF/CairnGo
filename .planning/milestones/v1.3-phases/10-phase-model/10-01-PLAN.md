# Phase 10 Plan 01 — read what a phase actually is

## Why

`roadmap_phases()` returns two lists of ints. That is why the board renders a
phase as `10` and why no amount of layout work can fill the empty space around
it: the data was never read. Everything the later phases want to show — what a
phase is about, how far it has got, what it waits on, what to run next — has to
exist before it can be laid out.

## Tasks

1. **Parse the roadmap properly.** Title, plan progress, requirement ids and
   completion date off the checkbox lines; milestone and plan counts off the
   progress table. Strip the completion suffix by shape, never by splitting on
   the dash.

2. **Read the disk.** `disk_state` from artifacts (none → planned → executed →
   verified), plan counts from `NN-NN-PLAN.md` / `NN-NN-SUMMARY.md` pairs when
   the roadmap does not carry them.

3. **Read the dependency graph.** Aggregate bd issue edges to phase level,
   handling both payload shapes; union with PLAN.md `depends_on:`. Derive
   `blocked_by` by removing dependencies already complete.

4. **Compute the next command** per phase from disk state, with complete
   phases returning nothing.

5. **Feed all three surfaces** from the one model, and prove it with a test
   that renders each and compares.
