<objective>
Wire cairn-lease.py to call cairn-journal.py's `lease` subcommand on every
GENUINE acquire/reclaim/release transition — never on a heartbeat-only
renewal, per D-01's scope (lease is one of the journal's three categories)
and D-02 (cairn-journal.py is the one writer; cairn-lease.py calls it,
never reimplements the append recipe itself).

Purpose: JOUR-02 needs "when did each side last move" to include the lease
side — a disk-vs-bd conflict can be born from a lease changing hands just
as easily as from an issue closing, and neither is a phase-directory
artifact transition on its own (per 16-CONTEXT.md's own framing). This
plan is the concrete source of the `lease` axis Plan 16-01's `last-moved`
subcommand already knows how to report.

Output: cairn-lease.py's `cmd_acquire`/`release_one`/`cmd_release --mine`
call `cairn-journal.py lease` on real transitions only, resiliently (a
journal failure never blocks the lease's own documented contract).
</objective>

  <behavior>
    - `cmd_acquire`'s `already_mine` branch (heartbeat renewal via
      `acquire` on a lease this worktree already holds): zero journal
      calls.
    - `cmd_acquire`'s fresh-create branch (no lease issue existed, or one
      existed but was vacant) and its `reclaimed` branch (stale lease
      taken over): exactly one `cairn-journal.py lease <phase> acquired
      --holder <new holder> --actor <resolved actor> [--prev-holder <old
      holder, only when reclaimed>] --project-dir <root>` call each.
    - `cmd_acquire`'s "held by another worktree, still fresh" branch
      (exits EXIT_HELD, writes nothing to bd): zero journal calls — no
      lease state actually changed.
    - `release_one`: when a lease issue existed and WAS held (a real
      release happens), exactly one `cairn-journal.py lease <phase>
      released --holder <the holder being cleared> --project-dir <root>`
      call. When no lease issue exists yet for the phase (the existing
      no-op branch): zero journal calls.
    - `cmd_release --mine`: one journal call per entry actually released
      in the loop (same shape as `release_one`), zero for phases that
      were not held by this worktree (already excluded from the `mine`
      list before the loop even starts).
    - `cmd_renew`: zero journal calls in every branch — this subcommand is
      explicitly heartbeat-only by contract (module docstring already
      says so) and must stay that way.
  </behavior>
  <action>
