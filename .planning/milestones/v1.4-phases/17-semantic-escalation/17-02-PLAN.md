<objective>
Wire the semantic half of the pipeline (D-01's middle layer): a
tool-restricted subagent that reads Plan 17-01's evidence bundle plus its own
further code/git/memory reads and returns a cited proposal AS TEXT (it holds
no tool capable of writing a file, full stop — see the revision note below),
and the `/cairn:reconcile <N>` command that orchestrates gate -> cache-check
-> collect -> spawn -> **write the proposal file itself** -> verify ->
present, never applying anything.

Purpose: this is where ESC-01 ("é possível pedir uma investigação que lê
código, história e memória e propõe uma reconciliação") actually happens —
Plan 17-01 only gathered the raw material. This plan also closes the second
half of ESC-02: Plan 17-01 proved the *deterministic* collector never writes
bd state; this plan proves the *semantic* investigator structurally cannot
either — not "constrained by instruction to one path," but holding no
write-capable tool at all.

**Revision note (plan-check blocker fix, superseding the original draft):**
the draft version of this plan granted the subagent `Write`, scoped to
`.cairn/conflicts.json` "in prose only." A plan check correctly rejected
that: this repo has no path-scoping syntax anywhere in its own agent
frontmatter or in the vendored GSD agents (the only tool-argument scoping
precedent, `Bash(git:*)`, lives in `settings.json` permission rules, not in
an agent's `tools:` list), so an unscoped `Write` grant plus an imperative
sentence lets the subagent write ANY file in the repo — exactly the
"instruction, not construction" trade D-01 rejected one layer down. The fix
taken is option (a) from the plan-check: drop `Write` entirely. The
subagent's tool grant is now `Read, Grep, Glob` — zero write-capable tools —
and it returns its proposal as its final message text; `/cairn:reconcile`
(a deterministic orchestration step, not the tool-restricted subagent)
writes `.cairn/conflicts.json` itself. Option (b), a `PreToolUse` hook
gating the write path, was considered and rejected: this repo has no
working precedent for agent-level `PreToolUse` hooks (only commented-out
examples exist in the vendored GSD agents), so it would introduce a new,
untested mechanism to guard the phase's central guarantee.

**"Zero invocations" proof, stated plainly (per plan-check's "noted, not
asked to fix"):** bats cannot spawn the Task tool, so ESC-04's "the
investigation runs only on a detected conflict" is proven at TWO different
strengths in this phase. Plan 17-01's `collect` refusal (exit 3 on a
non-conflict verdict) is bats-proven directly — the real, load-bearing
guarantee. This plan's Task 3 can only proxy-test that `/cairn:reconcile`'s
own PROSE checks corroboration before mentioning the subagent spawn — a
static line-ordering assertion on committed text, not a runtime proof that
the Task tool was never invoked. Do not read Task 3's ordering test as
equivalent proof to Plan 17-01's mutation/gating tests; it is a weaker,
necessary-but-not-sufficient check on the command's own wiring.

Output: `cairn/agents/reconcile-investigator.md` (the restricted subagent
definition, `tools: Read, Grep, Glob` only), `cairn/commands/reconcile.md`
(the orchestrating prose command, now including the file-write step),
`tests/cairn-reconcile-agent.bats` (structural/static checks — no real
subagent invocation happens in CI, per this codebase's existing constraint
that bats never invokes an LLM).

**Locked decisions this plan implements:**
- D-01: "subagente restrito → lê o pacote, escreve a proposta." Read literally
  this suggests the subagent itself writes the proposal file — but D-01's
  own recorded reasoning already anticipates exactly the trade a plan check
  caught in this plan's first draft: "rejeitado só-subagente com reescrita
  do critério: troca uma garantia verificável por uma que depende do
  harness cooperar." An unscoped `Write` grant "cooperating" with a prose
  instruction is precisely that dependency. This revision keeps D-01's
  three-layer shape intact while making the middle layer's write incapacity
  as verifiable as the collector's: the subagent contributes text
  (`claims[]`); the deterministic command layer performs the one file write,
  the same way it already performs every other deterministic step in this
  pipeline (gate check, `collect`, `verify`).
- D-02: the proposal is written to `.cairn/conflicts.json` (gitignored,
  reserved since v1.0) — this plan is the first thing that ever writes it,
  and (per the revision above) `/cairn:reconcile`'s own orchestration step
  is what performs that write, never the subagent directly.
- D-04: the cache lives in `/cairn:reconcile`'s own logic — before spawning
  the subagent, compare a fresh `collect --json`'s `evidence_hash` against
  any existing `.cairn/conflicts.json` for the same phase; a match means the
  cached proposal is still valid and the subagent is never re-invoked. The
  SAME `evidence_hash` this cache check computes is also what the command
  stamps into the proposal file it writes (see below) — never a value
  echoed back from the subagent's own text, keeping D-04's "a lista vem do
  coletor, não da narrativa do agente" principle intact for the hash field
  too, not just the source list.
- ESC-04's "roda apenas sobre conflito detectado" is enforced TWICE by
  construction: Plan 17-01's `collect` refuses mechanically (exit 3), and
  this command checks corroboration itself before calling `collect` at all
  — so a bats test against this command's own source can assert the gate
  check precedes every other step, without needing a live LLM (see this
  plan's `<objective>` for why that assertion is a proxy, not a full proof).

**Proposal schema (envelope fixed in 17-01; this revision splits authorship
between the deterministic command and the subagent — do not diverge):**
```
{
  "phase": <int>, "generated_at": <iso8601>, "evidence_hash": "sha256:<hex>",
  "claims": [{"statement": "...", "citations": [{"file":..., "line":..., "text":...}],
              "recommended_action": {"type": "bd_close"|"bd_reopen"|"manual_review", ...}}]
}
```
**Authorship split:** `phase`, `generated_at`, and `evidence_hash` are set by
`/cairn:reconcile` itself, from its own already-computed state (the phase
number it was invoked with, the current timestamp, and the exact
`evidence_hash` `collect` just produced) — never from the subagent's
output. The subagent's ENTIRE contribution is the `claims` array: its final
message text is a JSON object of the shape `{"claims": [...]}`, nothing
else, which `/cairn:reconcile` parses and merges into the envelope it
constructs and writes. The `recommended_action` vocabulary is intentionally
small and closed — `bd_close`/`bd_reopen` (Plan 17-03's applier executes
these two, and only these two, as real writes) and `manual_review` (no
automated action exists; Plan 17-03 enumerates it and does nothing else).
The subagent must never invent a fourth action type — instruct it
explicitly to pick one of exactly these three, mapped from corroborate()'s
own conflict source pairs (disk-vs-bd -> bd_close or bd_reopen depending on
which side is behind; roadmap-vs-disk and state_md-vs-disk -> manual_review,
since neither has a safe, generic automated fix — this mirrors how
cairn-doctor.py itself never auto-edits ROADMAP.md/STATE.md, only ever `bd`
subprocess writes).
