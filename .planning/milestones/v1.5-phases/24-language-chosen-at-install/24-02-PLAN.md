`cmd_set` de uma chave que tem `planning_key` no spec, **depois** de escrever
`.cairn/config.json` com sucesso, propaga para `.planning/config.json`:

  - se `.planning/config.json` **não** é arquivo existente → não faz nada, e o
    `--json` reporta `"propagated": false, "propagation_reason":
    "planning-config-absent"`. Esta é a condição inteira do M-1/M-2/M-3: propagar
    jamais pode criar `.planning/`, porque isso reclassificaria de D para A um
    repositório greenfield e faria a segunda execução do `/cairn:init` parar e
    desviar para `/cairn:migrate`;
  - se existe e é JSON lido com sucesso → `data[planning_key] = value` e reescreve
    com `json.dumps(data, indent=2) + "\n"`, **sem `sort_keys`**. Medido no
    `.planning/config.json` real deste repositório (2096 bytes): esse round-trip é
    byte a byte idêntico, então o diff da propagação é exatamente a linha da chave.
    Ordem preservada, nada reordenado. `"propagated": true`;
  - se existe mas não é JSON legível → **não escreve**, e reporta
    `"propagated": false, "propagation_reason": "planning-config-unreadable"`. O
    `set` no `.cairn/` já aconteceu e continua valendo; o `exit` segue 0 e a linha
    humana diz o que não foi propagado. Reescrever um arquivo ilegível destruiria o
    que estava nele — é a mesma razão pela qual `/cairn:config` para quando o `list`
    sai 3.

A linha humana do `set` ganha a metade da propagação, uma frase, dizendo o arquivo
e o resultado. Um mecanismo silencioso é indistinguível de um mecanismo ausente.

O docstring do módulo registra a propagação com as três medições nomeadas
(M-1/M-2/M-3) e a do round-trip. Docstring é especificação canônica aqui, e o que
foi **medido** fica separado do que foi **assumido**.

**Em `cairn/commands/init.md`, um passo novo entre o 3 e o 4** — antes do passo 6,
que é o hand-off. A posição é a decisão: `/gsd:new-project` spawna os próprios
subagentes (researcher, synthesizer, roadmapper), então perguntar depois dele é
perguntar depois de os primeiros subagentes do projeto já terem respondido na língua
errada. "Chosen at install" quer dizer antes do primeiro subagente.

O passo, na forma que o repositório já usa:

1. Ler o estado atual, do script e não de memória:
   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/scripts/cairn-config.sh" get agents.response_language --json
   ```
2. **`source` já é `file` ou `planning`** → há escolha feita. Diga qual é, em uma
   linha, **não pergunte e não escreve nada**, e siga. É o critério 3 do roadmap
   (um projeto já instalado não é alterado sem pedido) virando mecanismo em vez de
   intenção: a única porta que escreve é a pergunta, e a pergunta não abre.
3. **`source` é `default`** → uma `AskUserQuestion`, com **English pré-selecionado**
   e nomeado como o default. As opções cobrem as línguas comuns e deixam claro que
   qualquer nome de língua serve (`references/planning-config.md:238`: "Any language
   name"). Descreva o efeito, não o nome da chave: é a língua em que todo subagente
   escreve o que o usuário lê — relatórios, SUMMARYs, perguntas — enquanto código,
   caminhos e comandos ficam como estão.
4. Gravar com `cairn-config.sh set agents.response_language "<resposta>"`. O script
   propaga sozinho se `.planning/config.json` já existir (Task 1); nesta altura do
   fluxo greenfield ele não existe, e isso está dito ali.
5. **No passo 6, depois do `/gsd:new-project` voltar**, re-executar o **mesmo**
   `set` com o valor escolhido. Agora `.planning/config.json` existe e a propagação
   dispara. Idempotente por construção: mesmo comando, mesmo valor. Se o passo for
   pulado, o `/cairn:doctor` avisa (24-03) — a rede existe porque um passo em prosa
   é justamente o que falha.
