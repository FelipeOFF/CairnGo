A fatia fina atravessa `.planning/config.json` → `.cairn/config.json` → resolvedor →
subprocesso → payload de `prepare`, com **um** portador: a língua.

**No `cairn-config.py`.**

1. Tipo novo `"str"`. `valid_str(spec, value)`: `isinstance(str)`, não vazio depois
   de `strip()`, sem `\n` nem `\r`, e `len(strip()) <= spec["max_len"]`. Entra em
   `valid_value()` (leitura) e em `coerce_value()` (escrita, `die(EXIT_VALUE)` com a
   razão nomeada). A garantia existente continua valendo e vira teste: valor
   rejeitado sai 3 e **deixa o arquivo exatamente como estava**.

2. A chave, com o leitor nomeado:
   ```
   "agents.response_language": {
       "type": "str", "default": "English", "max_len": 40,
       "planning_key": "response_language",
       "reader": "cairn-parallel.py prepare",
       "effect": "...",
   }
   ```
   `planning_key` não é documentação: é o mecanismo do D-03 do CONTEXT — o nome da
   chave do GSD que **vence** esta quando estiver setada.

3. `effective(data, key, root)` ganha o `root` e a precedência. Antes de olhar o
   arquivo do cairn, se o spec tem `planning_key`, lê `.planning/config.json` por
   `planning_value(root, planning_key)`; valor presente e válido para o tipo →
   `(value, "planning")`. Senão a lógica de hoje, intocada.

   `planning_value()` é **defensivo e nunca morre**: arquivo ausente, ilegível, JSON
   inválido, ou raiz que não é objeto → `(None, False)`. Não é `die`. A razão é
   nomeada no código: o `.planning/config.json` é do GSD, não é nosso para validar,
   e um `get` que morresse por causa dele derrubaria o `batch` e o `prepare` que
   dependem dele. É a mesma disciplina do `effective()` de hoje, que degrada um
   valor de tipo errado em vez de falhar.

4. `cmd_list` e `cmd_get` passam `root`. `list` humano segue igual em forma; a
   origem `planning` aparece como as outras.

**No `cairn-parallel.py`.** `config_language(top)` — mesmo formato defensivo de
`config_value()` (subprocesso que não sobe, exit não-zero, JSON ilegível, payload
sem `value` → fallback), devolvendo `(value, source)`. O fallback é
`(None, "unavailable")` e **não** `("English", …)`: repetir o default aqui criaria
um segundo lugar onde ele mora, que é a coisa que esta fase inteira existe para não
fazer. `cmd_prepare` acrescenta ao `out`:
```
"response_language": lang,
"response_language_source": source,
```
e a saída humana ganha a linha correspondente — o operador lê essa saída antes de
spawnar, e um `unavailable` tem de ser visível ali, não só no `--json`.

**Os testes, e a quebra que cada um nomeia.**

Em `tests/cairn-config.bats`:
  - o literal do conjunto exato sobe de seis para sete, com o comentário de override
    ao lado (o 29-04 já fez isso por `jira.link`; a forma é a mesma e a intenção não
    muda: uma oitava chave não entra sem alguém ver). Quebra: chave nova sem leitor;
  - `get agents.response_language` sem config nenhuma → `English`, `source
    "default"`, `reader "cairn-parallel.py prepare"`. Quebra: default implícito;
  - `set` + `get` volta o valor gravado, `source "file"`. Quebra: a chave não é
    lida do arquivo;
  - com `.planning/config.json` dizendo `"Japanese"` e `.cairn/config.json` dizendo
    `"Portuguese"` → `get` responde `Japanese`, `source "planning"`. Quebra:
    precedência invertida — o caso em que os subagentes do cairn responderiam numa
    língua e os do GSD em outra na mesma execução;
  - `.planning/config.json` com JSON corrompido e `.cairn/` com `"Portuguese"` →
    `get` sai **0** e responde `Portuguese`. Quebra: um `die` no arquivo do GSD
    derruba `prepare`/`batch`;
  - `set agents.response_language ""` (e uma string de 41 caracteres) → exit 3 e o
    arquivo byte a byte como antes. Quebra: validação depois da escrita.

Em `tests/cairn-parallel.bats`, no ponto de entrega — `prepare --json` numa fixture
real, lendo o payload:
  - só `.cairn/config.json` = `Portuguese`, **sem `.planning/` nenhum** (o estado
    real da instalação greenfield) → `.response_language == "Portuguese"`,
    `.response_language_source == "file"`. Quebra: a chave do cairn não governa em
    lugar nenhum, isto é, é decorativa;
  - `.planning/config.json` = `Japanese` por cima → payload diz `Japanese`,
    `source "planning"`. Quebra: precedência;
  - nenhuma das duas → `English`, `source "default"`. Quebra: o default some do
    ponto de entrega;
  - `CAIRN_CONFIG` apontando para um stub que sai 3 → payload traz
    `response_language: null`, `source "unavailable"`, e `prepare` **sai 0**.
    Quebra: config quebrada derruba o `prepare`, ou pior, some em silêncio.

Cada teste do payload lê a saída do `prepare`, não o arquivo de config. Escreva
isso no cabeçalho do bloco, junto com o limite: `bats` não spawna o Task tool, então
nada aqui prova que o modelo colou o item no prompt — a mesma fronteira que
`reconcile.md:29-31` já registra.
